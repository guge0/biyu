## 一 「其他」到底是什么：OpenAI 兼容接口

必须先说清楚，否则「自己填」是填不进去的——填了地址还得知道按什么协议说话。

**中枢裁定：「其他」＝ OpenAI 兼容的对话接口**（`/v1/chat/completions` 那一套）。
这是事实标准：DeepSeek、Kimi、智谱新版、绝大多数第三方与本地部署（ollama、vLLM）都提供它。

界面上就写人话：`要能按 OpenAI 那套接口对话。本地跑的模型也可以，比如 http://127.0.0.1:11434/v1`

**TL 先答（¥0）**：现有四个 adapter 里，有没有哪一个已经是通用的 OpenAI 兼容实现、能直接复用？
- 有 → 「其他」几乎零成本，复用它、只是地址和模型 ID 由用户填
- 没有 → 要新写一个通用 adapter，**说清工作量再动手**

## 二 自定义模型不套推荐分工，且必须说出来

预置服务商我们知道哪个是推理模型、哪个是通用模型，所以能给推荐分工。
**自己填的，我们不知道它擅长什么。**

裁定：**选「其他」时，四个环节默认全用这一个模型**，并在落位回显里直说：

> 自己填的模型，我们不知道它擅长什么，所以每个环节都用它。想分开用，就在下面分别指定。

想分开的，去高级区各填各的模型 ID。

这不是回到中枢反对过的「统一模型」——那次反对是因为**我们明明知道分工却把它压平**；
这里是**我们确实不知道**，所以诚实地统一，并把这句话说出来。

## 三 「填错了给个连接错误」——这一条要拆开，因为「连不上」是最容易的那类错

老板说的方向对，但**连不上只是四类错里最好办的一类**。真正会咬人的是后面几类：

| 类别 | 现象 | 界面逐字 |
|---|---|---|
| 1 连不上 | 域名错、端口没开、超时 | `连不上 <地址>：<原因>。配置没有改动。` |
| 2 地址通但不是对话接口 | 填了网页地址、填了 embedding 端点，返回 200 但结构不对 | `这个地址回话了，但不像是对话接口。检查一下是不是少了 /v1。配置没有改动。` |
| 3 模型 ID 不对 | 对面明确说 model not found | `地址通了，但对面说：<原文>。把模型 ID 对着文档再看一眼。配置没有改动。` |
| 4 Key 不对 | 认证失败 | `<地址> 不认这把 Key。配置没有改动。` |

**还有第 5 类，校验时发现不了，必须诚实说明：**
连上了、能对话，但**上下文窗口太小、或者它是推理模型放在写作位**（Q-5 那个坑），
一句话的试连全都能过，真跑一章才炸。

→ 裁定两条：
1. **「试一下连接」不能只是 ping。** 要发一次**形状真实的最小请求**（带 system + user，
   要求它回几十个字），并把它回的话显示给作者看一眼——「它回了这句：…」。
   能不能对话，当场可见，比任何状态码都直观。
2. **界面明说做不到的那部分**，逐字：
   `连上了不代表它写得动一整章。第一次生成如果失败，回来换一个模型。`
   **不做能力探测**——那要花钱且不可靠。

## 四 一条安全提示（中枢加的，老板没提）

用户填的地址是任意的，**他的 API Key 会被发到那个地址**。填错一个字母就可能把 Key 发给陌生服务器。

→ 自定义区必须常驻一行提示，逐字：
`你的 Key 会发给上面这个地址。确认它是你信任的地方。`

**不禁止本机与内网地址**——本地跑模型正是常见用法，禁掉反而废掉一大类用户。

## 五 测试逻辑（老板问的，按常驻件四组）

### 第 1 组 · 行为
- 选「其他」填齐（地址 / 模型 ID / Key）→ **四个环节实际调用的都是这个模型**
  （断言的是实际调用，不是配置存进去了）
- 高级区给规划单独指定另一个模型 ID → 规划走它，其余仍走那个统一的
- 保存后重启服务，配置还在
- 从「其他」切回预置服务商 → **自定义配置保留但标「未启用」，不抹掉**
  （辛苦填的东西不许因为切一下就没了）
- 预置与「其他」不能同时生效，优先级明确且稳定

### 第 2 组 · 数据与目录（遍历，不抽样）
- **用户填的东西不写进 `models.yaml`**，写进用户配置层；断言预置清单不被污染
- 自定义模型出现在高级区下拉里，且与预置模型能区分（同名也要能分清）
- **地址的常见手滑要遍历**：末尾带 `/`、不带 `/`、带 `/v1`、不带 `/v1`、
  带 `http://` 与 `https://`、多余空格——每一种都要有确定行为（能用就规范化，不能用就报错）
- 遍历全部预置服务商 + 「其他」，断言每一个都有完整落位回显

### 第 3 组 · 错误与安全
- §三 的四类错各一条，断言**界面上出现了对应那句话**，不只是后端返回了错误码
- 每一类失败之后，**原配置一个字节没变**
- 超时有明确上限，不无限转圈
- **API Key 不出现在任何前端响应、日志、报错文案里**——自定义地址会被写进配置，
  这条要专门验一次（把地址写进日志容易，顺手把 Key 一起写进去也容易）
- 那行「Key 会发给这个地址」的提示在自定义态**常驻可见**

### 第 4 组 · 真实用户路径验收（中枢亲验）
**中枢给一个不花额外账号的自洽测法**：
> **用「其他」手填 DeepSeek 的官方地址与模型 ID，结果应当与直接选 DeepSeek 完全一致。**

同一把 Key、同一个端点，走「预置」和走「自己填」两条路，落位与实际调用必须一样。
这一条既验通路，又验「其他」没有走偏，而且**不需要第二家服务商的账号**。

另需整页截图（真起服务、真浏览器、1600×1000、不裁）：
1. 选中「其他」、字段展开、安全提示可见
2. 保存成功后的落位回显（含「我们不知道它擅长什么」那句）
3. 地址不对
4. 模型 ID 不对
5. Key 不对
6. 地址通但不是对话接口
7. 高级区给规划单独指定了另一个模型 ID
8. 窄窗口不溢出

**要花钱的那一项**：真跑一次生成，确认自定义配置下三个环节各自用的是什么模型。
